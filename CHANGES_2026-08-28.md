# Changes — 2026-08-28

CAN bus-off follow-up: after `restart-ms` fixes landed, the same board still failed to
connect every time it was plugged in. This session tracked that down and made the bus
recover from — rather than get stuck in — bus-off.

## 1. `can0` stuck permanently dead after bus-off

**Files:** `can_start_kvaser.sh`, `can_start.sh`, `can_bus_memo.md`

`ip -d link show can0` showed `can state BUS-OFF restart-ms 0`, confirmed by
`kernel: kvaser_usb 1-4:1.0 can0: bus-off` in `dmesg`/`journalctl`. Both bring-up scripts
brought the interface up without `restart-ms`, so once bus-off tripped, Linux disabled
automatic recovery and `can0` stayed dead until someone manually ran
`ip link set can0 down/up` — every single time, on every reconnect.

**Fix:** both scripts now bring `can0` up with `restart-ms 100`, so a bus-off auto-recovers
instead of requiring a manual reset.

## 2. Tried to prevent bus-off outright with one-shot mode — not supported on this hardware

In classic CAN, an unacked frame is retried by the controller **hardware** indefinitely at
full bus speed until it succeeds or the TX error counter hits bus-off (TEC > 255, i.e. ~32
failed attempts, a few milliseconds at 1 Mbit). `one-shot` mode (try each frame once, give
up silently on a miss) would prevent that outright.

> **Correction (2026-10-19).** This section originally claimed that pinging a single board
> that isn't wired up can trip bus-off, and that this is routine when bench testing with
> fewer than 30 boards connected. **That is wrong.** CAN acknowledgement is not addressed:
> every healthy node drives the ACK slot dominant for every frame it receives correctly,
> whatever ID is in the header. A frame aimed at an absent board is therefore still ACKed by
> any other live board and transmits normally — `cantest/test_comms.py` depends on exactly
> this. Bus-off requires that **no** node can ACK at all (nothing powered, bus unplugged,
> bitrate mismatch, or termination bad enough that no valid dominant level forms). See
> `CHANGES_2026-10-19.md`.

Added `one-shot on` to both bring-up scripts. Confirmed via kernel source
(`kvaser_usb_core.c`) that this Kvaser Leaf v3 (USB PID `0x0117`) uses the Hydra protocol
family, which supports `CAN_CTRLMODE_ONE_SHOT` — but only if the device firmware reports the
capability. Live test on the actual hardware:

```
RTNETLINK answers: Operation not supported
```

This unit's firmware doesn't report the capability, so the driver rejects it. Because
`ip link set` applies all attributes in one atomic netlink call, the failed `one-shot on`
took the whole command down with it — `can0` was left `DOWN`/`STOPPED`, not just missing
one-shot.

**Reverted:** removed `one-shot on` from both scripts (left a comment explaining why, so it
isn't re-attempted blind). `restart-ms 100` alone remains as the mitigation — bus-off can
still happen, but now it auto-recovers instead of requiring a manual reset.

**Still open:** actually preventing bus-off (not just recovering from it) needs a
software-side fix instead — e.g. throttling how many boards `scan_boards()`
(`cantest/communication.py`) pings back-to-back before listening for replies, so a burst of
misses against absent boards can't run the TX error counter to bus-off in one pass.

> **Done 2026-10-19** — ping batching landed in both `scan_boards()` and `poll_presence()`.
> Note the premise is narrower than written above (see the correction): the burst only
> matters when nothing on the bus can ACK. See `CHANGES_2026-10-19.md` §3.
