# Architecture

```
 ┌──────────────────────── Linux PC ────────────────────────┐
 │ cantest/main.py  (PySide6 GUI)                           │
 │   engine.py      100 Hz send loop + presence monitor     │
 │   wingcontrol.py samples u(x,y,t) at each motor position │
 │   communication.py  python-can / socketcan               │
 └──────────────┬───────────────────────────────────────────┘
                │ USB
          Kvaser Leaf v3  (can0, 1 Mbit/s, classic CAN)
                │ CAN bus (RJ45 on each board)
   ┌────────────┼────────────┬─────────── … ──┐
 board 1     board 2      board 3           board 30
 STM32G474 ── Lattice FPGA ── motor drivers ── 14 DC motors
     ▲                                            │
     └──────── 16 potentiometers (ADC) ◄──────────┘
```

The PC decides *where* every motor should be; each board independently runs a PID loop
per motor to *get* it there. If CAN goes quiet, boards keep holding their last setpoint.

> **Note:** classic CAN, not FD. FD was tried on 2026-06-22 and reverted after
> communication failed — but the unrelated boot-order bug (fixed 2026-08-11) was breaking
> communication at the time, so FD may deserve a retry (OPEN_ISSUES #2).

## Board hardware (summary)

Full notes: `memos/scheme-parts.md`, pinout in `memos/motor-dir-and-pwm.md`.

- **MCU:** STM32G474 at 160 MHz, 16 MHz crystal, REF3030 (3.0 V) ADC reference.
- **Power:** 12 V in → 3V3 / 5V bucks; motors on a separate adjustable ~6 V rail (SIC431,
  four voltage steps selected by two GPIOs — firmware uses mode 1, 6.06 V nominal); isolated
  5 V for the CAN/RS485 transceivers.
- **CAN:** ISO1042 isolated transceiver on the RJ45 port. The board design includes a 120 Ω
  terminator — see OPEN_ISSUES.md about termination with many boards.
- **Motors:** 16 PWM+DIR channels from the STM32 → Lattice FPGA → motor drivers. Only 14 are
  used (see numbering below).
- **Feedback:** one potentiometer per motor, on ADC1 (13 ch) + ADC2 (3 ch).
- **Board ID:** 6-bit DIP switch.
- Also on board, unused by current firmware: RS485, USB (CDC debug — handler commented
  out), EEPROM (I²C), SPI.

## Firmware (`App/`, `Core/Src/main.c`)

`Core/` is generated by STM32CubeMX from `STM32_code.ioc`. Hand-written code lives in
`App/`; edits in `Core/` must stay inside `/* USER CODE BEGIN … */` blocks or CubeMX will
erase them on regeneration.

| File | Role |
|---|---|
| `Core/Src/main.c` | Init sequence and the main loop |
| `App/Src/motor_helper.c` | ADC sampling, IIR filter, PID, PWM output, safety limits |
| `App/Src/can_helper.c` | CAN RX handler (opcodes), pong, telemetry stream |
| `App/Src/board_config.c` | Per-motor GPIO/timer tables, `active_motors`, `board_id` |
| `App/Src/dip.c` | DIP switch → CAN ID |
| `App/Src/timer_helper.c` | `get_time_us()` on TIM2 (1 µs ticks, 32-bit, wraps every ~71 min) |

### Boot sequence

1. HAL + clocks + peripherals (CubeMX).
2. Read DIP → `board_id`, **then** start FDCAN and enable the RX interrupt.

   > **Note:** the order matters: the board needs its ID before it can accept or answer
   > traffic (`CHANGES_2026-08-11.md`).
3. ADC calibration, start TIM2, DAC outputs the 2.5 V / 0.5 V limit thresholds, select the
   6 V motor rail, start PWM timers.
4. `position_init()`: take 1000 pot samples (~0.5–1 s) and set every motor's setpoint to
   where it currently is — the surface holds still at power-up.
   Position commands that arrive during this window are overwritten at its end.
5. Main loop: whenever >100 µs have passed, call `fix_motor_speeds()` and
   `CAN_Check_Bus_Off()` (restarts the CAN controller if it took itself off the bus).

### Control loop — `fix_motor_speeds()`

Every iteration, for all 16 motor indices:

1. **Sample:** start ADC1+ADC2 DMA and wait for both to finish (bounded at 2 ms; on timeout
   the last good values are kept and `adc_timeout_count` is incremented).
   `adc_index_map` reorders the 16 ADC results into motor order.
2. **Filter:** `pot_filtered = alpha·raw + (1−alpha)·pot_filtered`.
3. **Hard stop:** if `pot_filtered` is outside **[680, 3415]**, the motor is switched off and
   its PID state reset. (Unconnected channels read ~4095, so they are permanently "off".)
4. **Deadband:** if |error| < `deadband`, motor off, integral reset.
5. **PID** with measured `dt`, integral clamped to ±500, output negated (motor/pot polarity),
   clamped to ±`u_limit`, then raised to at least ±`min_pwm`.
6. **Output:** sign → DIR pin, magnitude → PWM compare (0..255, ~52 kHz PWM).
7. `CAN_Stream_Update()` sends a telemetry frame if streaming is on and the interval elapsed.

The loop *targets* 10 kHz, but the blocking ADC wait limits it to **~2 kHz** in practice
(measured with `HW_tests/adc_rate_test.py`). Alpha values are tuned for 2 kHz.

CAN reception is interrupt-driven (`HAL_FDCAN_RxFifo0Callback`) and only updates setpoints
and config variables; it never touches the motors directly.

### Safety layers (innermost first)

1. Firmware hard stop on measured position outside [680, 3415] ADC.
2. Firmware clamps every setpoint into [680, 3415].
3. DAC thresholds (2.5 V / 0.5 V) feed the board's hardware limit circuitry
   (`memos/scheme-parts.md`, "motor limitation").
4. Host-side per-motor range: `motor_min.csv` + `MOTOR_RANGE` (below).

## Host software (`cantest/`)

Python 3, PySide6, python-can (socketcan backend), numpy. Linux only (uses socketcan and
`/sys/class/net`).

| File | Role |
|---|---|
| `main.py` | Entry: channel picker (`gui/setup_window.py`) → `ControlMotor` → main window |
| `config.py` | All tunables: `BOARD_COUNT`, `UPDATE_HZ`, `MOTOR_RANGE`, spacings, file paths |
| `function.py` | **`motor_function(x_mm, y_mm, t)`** — the surface shape. Edit this to change behaviour. Must return values in [−1, 1] |
| `wingcontrol.py` | Evaluates `motor_function` at every motor's physical position |
| `engine.py` | `ControlMotor`: 100 Hz send thread, background presence monitor, config sending |
| `communication.py` | CAN I/O: `send_positions`, `scan_boards`, `poll_presence`, config, bus diagnostics |
| `limits.py` | Loads `motor_min.csv` and per-board `min_pwm` from the latest calibration |
| `gui/main_window.py` | Main window: grid of motor values, run controls, config sliders |
| `gui/calib_window.py` | "Edit limits" table editor for `motor_min.csv` |
| `test_comms.py` | Bench test: full 30-board send cycle against however many boards exist |

Choosing **DEMO-MODE** in the channel picker runs everything without hardware.

### Threads

- **Qt main thread:** GUI; a QTimer pulls the latest frame from the engine's queue to redraw.
- **Send loop** (`ControlMotor._send_loop`, while "Start dynamic" is on): every 10 ms,
  sample the shape at time `t`, send all positions, warn in red if the send took longer than
  the cycle.
- **Presence monitor** (`ControlMotor._monitor_loop`, always): pings missing boards plus a
  rotating subset of present ones each second; a board is dropped after 3 consecutive missed
  pings; backs off to 10 s if *no* board answers. It also re-sends controller config to any
  board whose pong says it hasn't received one since boot. Sends never wait on it.

  > **Note:** the back-off separates "one flaky board" (keep checking it every second) from
  > "bus is down" (no point flooding a dead bus with pings).

  > **Note:** config is re-sent automatically because the board keeps it in RAM only — any
  > reset, brown-out or re-flash silently reverts it to the firmware defaults.

### From shape function to motor position

```
motor_function(x_mm, y_mm, t)                   ∈ [−1, 1]
  x_mm = (board − 14.5)·10,  y_mm = (6.5 − motor)·10    (BOARD/MOTOR_SPACING_MM)
→ location = value·127.5 + 127.5                 ∈ [0, 255]    wingcontrol.py
→ byte = motor_min + location·MOTOR_RANGE/255    clamped 0..255   communication.scale_value
     (motor_min from motor_min.csv per motor, MOTOR_RANGE = 150)
→ CAN 0x01/0x02
→ ADC setpoint = 1048 + byte·7                   clamped [680, 3415]   firmware
```

`motor_max.csv` exists but **is not read** — the top of each motor's range is always
`motor_min + MOTOR_RANGE`. `REFACTORING = False` in `config.py` bypasses `motor_min`
scaling entirely (legacy).

## Motor numbering — four schemes, be careful

The same physical motor has a different number in each layer. Firmware indices 0 and 15
(hardware channels 1 and 16) are not driven by the host.

| Host / `motor_min.csv` | CAN slot | Firmware index (`motor_helper.c`, OpenOCD, `0x04` stream) | Hardware channel (`PWMn`/`DIR_n`, calibration JSON key, `M`n in calibration app) |
|---|---|---|---|
| m1 (Python index 0) | `0x01` byte 1 | 1 | 2 |
| m2 | `0x01` byte 2 | 2 | 3 |
| … | … | … | … |
| m7 | `0x01` byte 7 | 7 | 8 |
| m8 | `0x02` byte 1 | 8 | 9 |
| … | … | … | … |
| m14 (Python index 13) | `0x02` byte 7 | 14 | 15 |
| — | — | 0, 15 | 1, 16 (unused) |

The mapping lives in `active_motors[]` in `App/Src/board_config.c`. Pin and timer for each
hardware channel: `memos/motor-dir-and-pwm.md` (its PWM table is current; its prescaler
note is not — the timers now run at prescaler 12, ~52 kHz).

## FPGA (`lattice_code/`)

The Lattice FPGA sits between the STM32's PWM/DIR outputs and the motor drivers. The
Verilog (`scaled_digital_*.v`, `digital_on.v`) converts each PWM+DIR pair into the
two-input drive the motor driver (DRV8833-type) expects, and contains a pot combiner. It is
programmed separately with Lattice Diamond over JTAG (connector X7). Which `.v` variant is
currently flashed on the boards is not recorded anywhere — confirm with whoever programmed
them before changing it.

## Hardware test tools (`HW_tests/`)

| Tool | Needs | Purpose |
|---|---|---|

| `step_response_test.py` | CAN | Step one motor, record via telemetry stream, fit τ |
| `board_calibration.py` | CAN | Older single-board CLI calibration |
