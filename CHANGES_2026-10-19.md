# Changes — 2026-10-19

Follow-up to the 2026-08-28 bus-off session. The mitigation that landed then (`restart-ms`)
was sound, but the *explanation* recorded alongside it was wrong, which made bus-off look
like a routine event to be papered over rather than a fault to be found. This session fixes
the model, makes the failure say what it actually means, bounds the one burst that can
genuinely matter, and clears two bugs that stopped the GUI from starting at all.

## 1. Corrected the bus-off model

**Files:** `CHANGES_2026-08-28.md`, `can_start_kvaser.sh`, `can_start.sh`

The previous notes and both bring-up scripts stated that pinging a board that isn't wired up
can trip bus-off, and that this is routine when bench testing with fewer than 30 boards.
That is wrong.

**CAN acknowledgement is not addressed.** Every error-active node drives the ACK slot
dominant for every frame it receives correctly, whatever ID is in the header. A ping aimed
at absent board 30 is ACKed by boards 1–29 and transmits normally. `cantest/test_comms.py`
has always depended on this — "the 29 frames for non-existent boards are ACKed by the real
board in hardware."

When **no node can ACK at all** (nothing powered, bus disconnected), the controller
retransmits the frame at full line rate and its TX error counter climbs to
**ERROR-PASSIVE** (TEC >= 128) — and then *stops there*. ISO 11898 exempts ACK errors from
further TEC increments once a transmitter is error-passive, precisely so a lone node isn't
driven off the bus just because nobody is listening. It keeps retrying the same frame
indefinitely at ERROR-PASSIVE, and drops back to ERROR-ACTIVE once something ACKs.

*Correction made during the bench test (same day):* an earlier draft of this section said
no-ACK runs straight to bus-off in ~32 attempts. The bench test disproved it — with the
board unpowered, the Kvaser went to ERROR-PASSIVE and stayed there, bus-off count 0.

So **bus-off needs real bit errors**, not just silence:

- bitrate mismatch between nodes
- wiring/connector faults, or termination bad enough to corrupt bits
- a node corrupting frames — e.g. a board powering up or resetting while traffic is on
  the wire

**This reproduced the 2026-08-28 bus-off on the bench.** With the board unpowered, the
Kvaser sat at ERROR-PASSIVE retransmitting an unacked ping nonstop. Plugging the board's
power back in tripped bus-off immediately (`14:49:02 kvaser_usb ... can0: bus-off, scheduling
restart in 100 ms`): the board powering up mid-retransmission corrupts the frame, and those
are real bit errors. That matches the August symptom — "plugging in a board that had worked
before." `restart-ms 100` recovered it automatically and the board was found on the next
scan. Prevention isn't really possible from the host side (the frame is already in the
controller); recovery is the right answer, and it works.

**Driver quirk found at the same time:** after that auto-recovery, `ip -details link show
can0` kept reporting `can state BUS-OFF` even though frames were transmitting and being
answered normally (TX counter advancing, pongs received). The Kvaser driver doesn't update
its reported state after a restart-ms recovery. So the reported state can't be trusted as
proof the bus is down — see §3 for what the scan uses instead.

Also clarified what `restart-ms 100` actually costs, because "re-upping the bus" was the
worry that prompted this session. It is a *local controller* restart, not a re-init: the
interface stays up, open sockets survive, bitrate/txqueuelen are untouched, and the other
boards see nothing but an idle bus and keep holding their last commanded `desired_position`
(the PID in `motor_helper.c` runs regardless of CAN). Cost is ~100 ms, about 10 dropped
frames at the 100 Hz command rate — the surface freezes briefly, it does not jerk or go
limp. It is recovery, not prevention.

**Hardware item to confirm (low priority).** `memos/scheme-parts.md` notes the board has a
120R CAN terminating resistor. A CAN bus wants exactly two, one at each end, so on a
multi-board bus it should be fitted or enabled only on the two end boards. This is very
likely already handled in the design (jumper, switch, or not populated on most boards) —
the memo just doesn't say. Irrelevant with one board on the bench. Before wiring up many
boards, confirm with the board designer that the terminator can be disabled per board.

## 2. Bus failures now say what they mean

**File:** `cantest/communication.py`

A bare `CanError` repr can't distinguish "one board is unplugged" from "nothing on this bus
can acknowledge anything", which per §1 is the only distinction that matters.

- Added `read_can_state(channel)` — reads the kernel's view via `ip -details link show`.
  python-can's `bus.state` is unusable here: the socketcan backend doesn't override
  `BusABC.state`, which unconditionally returns `ACTIVE` whatever the hardware is doing.
  Degrades to `None` (no guess) for a non-CAN or missing interface.
- Added `MotorCommunication.bus_state_hint()` — turns `BUS-OFF`/`STOPPED` into the four
  things to actually check (board power, bus plugged in, bitrate, termination count), and
  `ERROR-PASSIVE`/`ERROR-WARNING` into "the bus is marginal, fix it before it trips".
- Wired into the existing throttled `CAN send failed` path, so it inherits the
  once-per-second rate limit and can't flood.

## 3. Bounded the ping burst

**File:** `cantest/communication.py`

`scan_boards()` queued all 30 pings before listening, and `poll_presence()` did the same
whenever every board was missing. Per §1 this only matters on a bus where nothing can ACK —
the startup-into-a-dead-bus case — where there's no point handing the controller a 30-frame
burst to retry.

- Both now ping in batches of 5 (`batch_size`) with a listen window after each.
- `scan_boards()` additionally aborts early if a batch gets no pong **and** the interface's
  TX counter (`/sys/class/net/can0/statistics/tx_packets`, via `read_tx_packets()`) didn't
  advance — i.e. not one ping was ACKed by anything. A frame only counts as transmitted once
  some node ACKs it, so this is direct evidence that nothing on the bus is alive, and unlike
  the reported state it can't go stale (§1). Bench-checked: 5 pings addressed only to absent
  boards 2–6 all counted as transmitted, ACKed by board 1, so a fleet whose first batch
  happens to be all absent won't trip a false stop. — instead of grinding through every remaining
  batch. The state check only runs while nothing has answered, so a healthy fleet never
  pays for it.
- `timeout` is now the window *per batch*, so `scan_boards()`'s default dropped 0.3 → 0.15 s
  to keep the worst case bounded: ceil(30/5) × (1+1) × 0.15 = 1.8 s with nothing answering,
  versus 0.6 s before. A pong round-trip is well under a millisecond, so 0.15 s for 5 boards
  is still ~150× margin, and a healthy batch returns as soon as its last board replies.

Unchanged and still doing the heavy lifting: `send_positions()` writes nothing at all once a
scan has found no boards, and `engine.py:_monitor_loop` backs off 1 s → 10 s when the whole
bus looks dead.

## 5. Bus-load budget at 30 boards (predicted, never measured)

As with termination in §1: with one board on the bus, load has never been a factor.
At 30 it is, and the arithmetic is not reassuring.

A classic-CAN standard-ID frame with 8 data bytes is 108 bits, plus 3 bits of interframe
space, plus bit stuffing — call it ~118 bits, so ~118 us at 1 Mbit.

`send_positions()` sends two frames per board (opcodes `0x01` and `0x02`, 7 motors each), so
a full cycle is 60 frames:

- 60 x ~118 us = **~7.1 ms of wire time per cycle**
- against the 10 ms budget of `UPDATE_HZ = 100` → **~70% bus utilisation**

CAN is usually kept under 30-40% so arbitration and retries have room. At 70% there is
~2.9 ms of slack for the background presence polling, any telemetry streaming (`0xA0`), and
retransmissions — and `engine.py` already prints `WARNING: send_positions took ... ms` when a
cycle overruns, so that warning is likely to fire more or less continuously once the fleet is
connected. Nobody has seen it at scale because nobody has run more than one board.

**Cheapest lever if it does:** `UPDATE_HZ` 100 → 50 halves utilisation to ~36%, and costs
nothing real — `HW_tests/NOTES_2026-06-15.md` puts motor mechanical bandwidth under 20 Hz, so
100 Hz is already ~5x oversampled. Other options (only sending boards whose values changed,
or CAN FD — tried and reverted in June) are more work for less certain benefit.

Worth measuring rather than assuming: `cantest/test_comms.py` exists precisely to run the
full 60-frame cycle against a single real board, so the timing half of this can be checked on
the bench today, before the fleet exists.

## Verification status

Tested: both files compile; `load_all_limits()` arity confirmed at 3; batching verified at
5/5/5/5/5/5 for 30 boards and on short and zero-size inputs; `read_can_state` returns `None`
for a missing device and for a non-CAN device (`lo`) rather than guessing; full demo-mode
scan/poll/send path; and the real (non-demo) socket path against a stubbed bus — confirming

interface reports bus-off, and 0 frames sent by `send_positions()` after a failed scan.

**Bench test on real hardware (one board, Kvaser Leaf v3):**

1. Board powered: scan finds `[1]` in 1.81 s (29 absent boards time out), bus ERROR-ACTIVE
   before and after, 0 bus errors. Background `poll_presence()` takes ~0.9 s per call with
   29 missing (6 batches x 0.15 s) — harmless, it runs in its own thread and sends don't
   wait on it.
2. Board unpowered: the Kvaser went to ERROR-PASSIVE, not bus-off (bus-off count 0). The
   first version of the early stop only watched for BUS-OFF and so never fired; fixed to
   include ERROR-PASSIVE. Retest: scan stops after the first batch in 0.16 s and prints the
   "nothing on the bus is acknowledging" hint.
3. Board powered back on: bus-off on plug-in (see §1), auto-recovered, board 1 found. The
   reported state stayed BUS-OFF afterwards, so the early stop was switched from the
   reported state to the TX counter. Rescan with board on: `[1]` found, no false stop.
4. Board unpowered again, TX-counter version: 0 frames ACKed, scan stopped after the first
   batch in 0.15 s with the "nothing on the bus is acknowledging" message. (Reported state
   was still the stale BUS-OFF going in — the check ignored it, as intended.)
